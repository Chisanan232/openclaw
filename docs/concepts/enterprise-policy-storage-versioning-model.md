# Enterprise policy storage and versioning model

## Goal

Define how enterprise policy bundles are stored, versioned, reviewed, activated,
superseded, and rolled back so runtime policy enforcement can operate on stable,
auditable bundle versions instead of mutable config blobs.

The canonical model is implemented in:

- `src/shared/enterprise-policy-storage-versioning-model.ts`

## Policy bundle lifecycle states

`CONCLAW-50` defines these policy bundle states:

- `draft`
- `active`
- `superseded`
- `rolled_back`

State transitions are constrained by `canTransitionPolicyBundleState(...)` so
activation and rollback flows stay explicit.

## Storage model and scope layering

Each policy document captures:

- organization and optional workspace targeting
- scope layer (`organization` or `workspace`)
- layering mode (`org_only`, `workspace_only`, `org_then_workspace`)
- explicit version + version label
- review metadata and activation/supersession/rollback references
- policy entries with target/effect/reason metadata

Layer resolution precedence is normalized by:

- `resolvePolicyLayerPrecedence(...)`

## Activation and rollback rules

Activation checks (`checkPolicyActivation(...)`) enforce:

- only `draft` bundles can be activated
- review must be `approved` or `not_required`
- active bundle scope exclusivity (same scope cannot have two active bundles)

Rollback checks (`checkPolicyRollback(...)`) enforce:

- rollback target must be `active`
- rollback candidate must be `superseded` or `rolled_back`
- target and rollback candidate scopes must match

## Rollout semantics

Rollout can be:

- `immediate` (single 100% phase)
- `phased` (deterministic sequence with percentage milestones)

Rollout plans are generated by:

- `buildPolicyRolloutPlan(...)`

## Admin, approval, and audit linkage

Admin operations are mapped in:

- `ENTERPRISE_POLICY_ADMIN_OPERATIONS`

These mappings provide stable anchors for:

- admin policy management API endpoints
- admin UI flows
- approval and audit attribution for policy activation/rollback decisions

Audit linkage types are defined via `EnterprisePolicyAuditLink` so policy
change events can reference immutable bundle/version context.

## Verification baseline

Acceptance checks are encoded in:

- `src/shared/enterprise-policy-storage-versioning-model.test.ts`

The tests validate:

- admin operation coverage
- lifecycle transition rules
- activation/rollback safety checks
- scope layering precedence
- deterministic phased rollout schedule generation
